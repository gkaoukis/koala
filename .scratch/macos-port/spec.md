# macOS native execution support

## Problem Statement

Koala's benchmarks only run natively on Debian-based Linux. A contributor on macOS can only exercise the suite by routing everything through the Docker image, which means macOS itself is never actually the platform being measured — it's just a host for a Linux container. That's insufficient for using macOS as a genuine target for characterizing shell/OS behavior (Koala's stated research purpose), and it blocks a macOS-based contributor from developing or validating benchmark changes against their own machine directly. Separately, benchmark and harness scripts currently assume GNU coreutils and bash are present, which is true on Debian but not guaranteed even on other Linux distributions (a second contributor is porting to Fedora concurrently) and is false by default on macOS (BSD userland, bash 3.2).

## Solution

Make `./main.sh <benchmark> --bare --min` (and, benchmark-by-benchmark, `--small`/`--full`) work end-to-end on macOS using the host's own shell and utilities — not routed through Docker — validated the same way Linux runs already are: via each benchmark's existing `validate.sh` hash comparison. This requires (1) bringing the harness scripts to strict POSIX-sh conformance so they run under any POSIX shell rather than assuming bash, (2) adding macOS-specific dependency installation to each benchmark's `install.sh` behind OS detection, (3) providing GNU-equivalent behavior for `sed`/`grep`/`find`/`awk` etc. on macOS without editing the ~90 benchmark workload scripts, and (4) giving Linux-only benchmarks (where no macOS equivalent exists) a clear, self-contained way to skip themselves.

## User Stories

1. As a macOS-based contributor, I want `./main.sh <benchmark> --bare --min` to run without Docker, so that I can develop and test benchmark changes directly on my machine.
2. As a macOS-based contributor, I want `./setup.sh`/each benchmark's `install.sh` to install the correct dependencies for my platform automatically, so that I don't have to manually translate Debian package names to Homebrew formulae myself.
3. As a researcher, I want workload scripts under `scripts/*.sh` to remain runnable under any POSIX-conformant interpreter set via `$KOALA_SHELL` (bash, dash, zsh, an experimental research shell), so that cross-interpreter comparisons stay valid after the macOS port.
4. As a maintainer, I want the harness (`main.sh` and each benchmark's five-script contract) to run under strict POSIX `sh`, so that behavior doesn't silently depend on bash being present or being a particular version.
5. As a maintainer, I want GNU-flavored `sed`/`grep`/`find`/`awk` usage in existing benchmark scripts to keep working unmodified on macOS, so that I don't have to audit and edit ~90 script files to add indirection.
6. As a maintainer, I want the GNU-utility substitution to use real Homebrew-installed GNU tools rather than approximating BSD-tool behavior, so that `validate.sh` hash comparisons against existing baselines keep passing.
7. As a macOS-based contributor, I want the `PATH` modification that exposes GNU tools to apply only for the duration of a benchmark run, so that my normal shell environment and other tools on my machine are never permanently altered.
8. As a maintainer, I want the GNU-utility shim to work transparently regardless of what `$KOALA_SHELL` is set to, so that swapping the interpreter under test doesn't require separate platform-compatibility handling.
9. As a maintainer, I want each of the five per-benchmark stage scripts (`install.sh`/`fetch.sh`/`execute.sh`/`validate.sh`/`clean.sh`) to set up its own OS-detection and PATH shim independently, so that each stage remains runnable in isolation per the documented manual workflow (`cd <benchmark>; ./install.sh; ...`).
10. As a maintainer, I want OS-detection logic in `install.sh` shared via a single sourced helper rather than duplicated inline per file, so that a future fix to the detection heuristic doesn't require touching every benchmark.
11. As a maintainer coordinating with a concurrent Fedora port, I want each `install.sh`'s OS-specific package installation to follow a fixed `case` skeleton with all three OS branches always present, so that both ports can add branches to the same file without repeatedly colliding on the same lines.
12. As a maintainer, I want package-name mapping (e.g. apt's `libncurses5-dev` vs. brew's `ncurses`) to stay inline per `install.sh` rather than centralized in a shared abstraction library, matching the decision to prioritize merge-safety over deduplication for now.
13. As a maintainer, I want a benchmark that has no reasonable macOS equivalent (e.g. `pkg/scripts/pacaur.sh`, which builds Arch `PKGBUILD` files into `.deb` packages via `makedeb` — a tool with no macOS support at all) to detect this itself at runtime and exit early with a clear message and log output, rather than failing with a confusing build error mid-run.
14. As a CI maintainer, I want the Linux-only skip behavior to be self-contained in the script (not a separate manifest `main.sh`/CI has to consult upfront), consistent with this port's general preference for inline logic over shared abstractions.
15. As a maintainer, I want the POSIX-sh conformance pass on harness scripts done as a prerequisite step before the macOS-specific OS-detection/install-branch work lands, so the OS-port conditionals are added to already-stable files instead of two waves of edits touching the same lines.
16. As a maintainer, I want workload scripts under `scripts/*.sh` to be treated as already POSIX-conformant by default, with any non-conformant one fixed opportunistically when discovered, rather than wholesale-audited upfront before any port work can start.
17. As a maintainer, I want the macOS port validated using the existing `./main.sh <benchmark> --bare --min` + `validate.sh` hash-check mechanism, benchmark by benchmark, so that no new test infrastructure needs to be built or maintained.
18. As a contributor running the macOS validation sweep, I want the `net/` benchmark explicitly excluded from automated runs, so that I don't accidentally alter live firewall/NAT rules on my own machine (`net/execute.sh` adds/removes `iptables` MASQUERADE rules directly).
19. As a future contributor porting to a fourth OS/shell target, I want the fixed `case` skeleton and self-contained per-stage-script pattern established here to be the template to follow, so that onboarding a new platform doesn't require redesigning the approach.

## Implementation Decisions

- **Scope**: native (`--bare`) execution on macOS is the target, not just Docker-mediated access (Docker already works cross-platform and isn't what "runnable on macOS" is meant to add). Validated with `--min` inputs.
- **POSIX conformance pass** (see ADR-0003): `main.sh` and every benchmark's five-script contract (`install.sh`/`fetch.sh`/`execute.sh`/`validate.sh`/`clean.sh`) are converted from `#!/bin/bash` to `#!/bin/sh` with POSIX-conformant dialect, preserving existing behavior exactly. An audit of 91 such files found only 11 containing actual bash-only constructs (`EUID`, `[[ ]]`, `pipefail`, `BASH_SOURCE`, `shopt`); the rest need only a shebang change. This pass happens first, before any OS-detection/install-branch work lands, with no formal cross-contributor coordination beyond that sequencing. As a side effect this resolves `web-search/validate.sh`'s prior bash-3.2 incompatibility (`declare -A`/`mapfile`). Workload scripts under `scripts/*.sh` are assumed already POSIX-conformant (they're invoked as `$KOALA_SHELL "$BENCHMARK_SCRIPT"`, so their own shebang is never consulted — only dialect matters); any found non-conformant during implementation are fixed individually, not audited upfront.
- **OS-detection and install branching** (see ADR-0001): a single shared, sourced helper performs OS detection (e.g. exposing something like `$KOALA_OS`); it is not duplicated per file. Each benchmark's `install.sh` sources this helper and branches on it using a fixed skeleton — `case "$KOALA_OS" in debian) ... ;; macos) ... ;; fedora) ... ;; esac` — with all three branches always present (even a Fedora stub before that port lands), agreed specifically to minimize merge collisions with the concurrent Fedora port touching the same ~29 files. Package-name mapping (apt name → brew formula name) stays inline within each file's macOS branch; no centralized package-mapping library is introduced.
- **GNU utilities on macOS** (see ADR-0002): the macOS branch of `install.sh` installs GNU coreutils/sed/grep/findutils/gawk via Homebrew, then populates a private shim directory (e.g. `$TOP/.tools/gnubin`) with plainly-named symlinks (`sed` → `gsed`, `grep` → `ggrep`, `find` → `gfind`, `awk` → `gawk`, …). Each of the five stage scripts independently prepends this directory to `$PATH` at the top of the script — not just `main.sh` — so every stage remains self-contained and runnable standalone. `$PATH` is never modified globally (no shell rc file edits, no symlinks into a global bin directory); the change is scoped to the process tree of a single run. Because `execute.sh` exports the modified `PATH` before spawning `$KOALA_SHELL "$BENCHMARK_SCRIPT"`, this is transparent to whatever interpreter is under test. Env-var indirection (`$SED`/`$GREP`/`$FIND`/etc., called explicitly by scripts) is kept only as a fallback for cases PATH substitution can't reach — chiefly, any script invoking a utility by hardcoded absolute path rather than bare command name. No exhaustive upfront audit for these was done; they are identified and patched individually as found during implementation.
- **Linux-only benchmarks**: `pkg/scripts/pacaur.sh` is confirmed non-portable — `makedeb` (which it shells out to) has no macOS support and produces `.deb` packages requiring `dpkg`/`apt`, infrastructure that doesn't exist on macOS; there is no faithful substitute that would preserve the same benchmark dataset (Arch `PKGBUILD`s fetched from `atlas.cs.brown.edu/data/aurpkg`). The script itself checks the platform (`uname`) at runtime and exits early with a clear "skipped: not supported on this platform" message plus log output, consistent with the inline-conditional style used throughout this port. No upfront manifest or CI-level declaration mechanism is introduced. Other benchmarks suspected of similar Linux-coupling (e.g. `repl/scripts/vps-audit.sh`, a Linux VPS security audit tool) should be checked for the same treatment during implementation, on a case-by-case basis, not assumed in advance.

## Testing Decisions

- The acceptance mechanism is the existing one: `./main.sh <benchmark> --bare --min` (and `--small`/`--full` where already supported) run on macOS, checked against that benchmark's existing `hashes/` via its `validate.sh` — the same mechanism already used for Linux in CI (`.github/workflows/tests.yml`). No new test infrastructure is introduced; portability is proven by the suite's existing correctness oracle, not a separate one.
- No standalone unit tests are added for the OS-detection helper or the GNU-utility shim in isolation — per ADR-0001's decision against a shared abstraction layer, these are exercised indirectly through the per-benchmark `--bare --min` runs, which is the highest and only seam used.
- **`net/` is excluded from any automated or sweep-style validation run on macOS.** `net/execute.sh` adds/removes `iptables` NAT/MASQUERADE rules directly against the host's live firewall/network state; `net/scripts/accept-ips.sh` and `portscan.sh` are firewall/network-scanning workloads. These must not be run unattended during this port's validation, on macOS or otherwise, without explicit manual review of what they'll change on the machine running them.
- The 11 harness scripts identified as containing actual bash-only syntax are the ones requiring behavioral verification (not just a shebang swap) after the POSIX conversion — these should be spot-checked against their pre-conversion behavior specifically.

## Out of Scope

- Fedora support — being handled by a separate contributor; this spec only commits to a coordination-friendly shape (the fixed `case` skeleton) for their work to land into, not to the Fedora branches themselves.
- A CI job on a `macos-latest` runner — not decided in this round; the existing Linux CI matrix is unaffected by this spec.
- Any centralized OS/platform abstraction library — explicitly rejected for now (ADR-0001); may be revisited once both the macOS and Fedora ports have landed and the duplication cost is visible in practice.
- Porting `pkg/scripts/pacaur.sh`'s actual workload to macOS — determined infeasible; only its skip behavior is in scope.
- A full upfront audit of all ~90 `scripts/*.sh` workload files for POSIX conformance or absolute-path utility invocations — both are handled opportunistically as discovered during implementation, not as a preceding audit phase.
- Porting or adapting `net/`'s firewall-manipulating workload to macOS (`iptables` has no direct macOS equivalent — `pfctl` is structurally different) — out of scope entirely for this round.

## Further Notes

- Three ADRs were produced alongside this spec and should be read alongside it: `docs/adr/0001-inline-per-os-conditionals-in-install-sh.md`, `docs/adr/0002-gnu-utilities-via-path-shim.md`, `docs/adr/0003-posix-conformance-pass-before-os-ports.md`.
- The sequencing dependency is real: ticket 01 (POSIX conformance) should land before tickets 02–04 (OS detection, GNU shim, install branches) begin, per ADR-0003.
- If further Linux-only benchmarks are found during implementation beyond `pacaur.sh`, apply the same self-detection-and-skip treatment rather than reopening the upfront-declaration-vs-self-detection decision.
